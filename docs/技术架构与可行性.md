# camera-scanner 技术架构与可行性文档

> 基于 **Tauri 2.0 + React (TypeScript)** 的网络摄像头安全审计与实时预览桌面工具。
> 参考项目：[Ingram](https://github.com/jorhelp/Ingram)（摄像头漏洞扫描框架）、[scan-for-webcams](https://gitcode.com/gh_mirrors/sc/scan-for-webcams)（暴露摄像头探测）。

---

## 0. 使用范围与合规声明（务必先读）

本工具定位为 **面向授权环境的安全审计工具**，只能用于以下场景：

- 你本人拥有的摄像头 / NVR / 网段；
- 你已获得资产所有者**书面授权**的渗透测试 / 安全评估目标。

明确禁止：对未授权的公网 IP、他人网络或设备进行扫描、探测、凭据尝试或视频访问。未授权访问计算机信息系统在中国《网络安全法》《刑法》第 285/286 条及多数司法辖区均属违法。本项目在设计上采取以下约束以降低滥用风险：

- 默认 **只允许扫描私有网段**（RFC1918：`10/8`、`172.16/12`、`192.168/16`）与显式加入白名单的目标；扫描公网段需要在设置中二次确认并留存操作日志。
- 漏洞核查模块只做 **版本指纹识别 + 已知漏洞比对并给出加固建议**，不内置可直接 getshell 的攻击载荷。
- 所有扫描行为写入本地审计日志（时间、目标、操作者），便于合规追溯。
- 首次启动强制展示授权确认弹窗。

> 与参考项目的差异：Ingram / scan-for-webcams 面向"发现互联网上暴露的摄像头"，本项目收敛为"对自有/授权资产做安全自查与集中预览"。

## 2. 总体架构

```
┌───────────────────────────────────────────────────────────────┐
│                       Tauri Desktop App                         │
│                                                                 │
│  ┌──────────────────────────┐        ┌───────────────────────┐ │
│  │  Frontend (React + TS)    │  IPC   │  Backend (Rust)        │ │
│  │  ──────────────────────   │◀──────▶│  ─────────────────     │ │
│  │  · 目标/白名单管理 UI      │ invoke │  · 发现引擎 (discovery)│ │
│  │  · 扫描进度 / 结果表格     │ event  │  · 探测/指纹 (probe)   │ │
│  │  · 实时预览 (MSE/WebRTC)   │        │  · 漏洞比对 (audit)    │ │
│  │  · 报告与导出             │        │  · 流媒体网关 (stream) │ │
│  └──────────────────────────┘        │  · 存储 (sqlite)       │ │
│                                       └───────────┬───────────┘ │
│                                                   │             │
└───────────────────────────────────────────────────┼─────────────┘
                                                    │ 网络 (仅授权网段)
                                     ┌──────────────▼──────────────┐
                                     │  摄像头 / NVR (RTSP/ONVIF/HTTP) │
                                     └───────────────────────────────┘
```

- **前端**：只负责交互、可视化、播放。不直接发起网络扫描，所有网络行为经由后端命令，便于统一限速、白名单校验与审计。
- **后端（Rust）**：承载全部网络 I/O、并发调度、流媒体转封装，通过 Tauri `command` 暴露能力、通过 `event` 推送实时进度与结果。
- **进程模型**：单进程 + 多异步任务（Tokio）。流媒体转码如走 ffmpeg，则以 **sidecar 子进程** 方式运行。

## 3. 关键技术方案

### 3.1 设备发现（discovery）

多手段并行，结果去重合并：

1. **ONVIF WS-Discovery**：向组播地址 `239.255.255.250:3702` 发送 `Probe`（UDP/SOAP），解析 `ProbeMatch` 得到 ONVIF 设备的 `XAddrs` 服务地址。这是识别标准 IPC 最可靠的方式。
2. **mDNS/Bonjour**：监听 `_rtsp._tcp` / `_http._tcp` 等服务，发现支持零配置的设备。
3. **端口探测兜底**：对授权网段做 TCP connect 扫描常见端口：`554`(RTSP)、`80/8000`(海康 Web)、`37777`(大华私有)、`8899`、`443`。用 `tokio` 并发 + `Semaphore` 限制并发数与速率。

### 3.2 指纹识别与漏洞比对（probe / audit）

- **指纹**：读取 HTTP `Server` 头、登录页特征、ONVIF `GetDeviceInformation`（厂商/型号/固件版本）、RTSP `OPTIONS` 响应。
- **漏洞比对**：维护本地 YAML/JSON 漏洞规则库，字段包含 `厂商 / 影响固件版本范围 / CVE 编号 / 风险等级 / 加固建议`。匹配到即在结果中标注风险，并给出"升级固件 / 关闭公网映射 / 修改默认口令"等建议。
  - 覆盖参考项目涉及的典型条目（仅做**存在性判断与提示**，不含利用链）：Hikvision CVE-2021-36260、Dahua CVE-2021-33044/33045、部分 dlink/宇视历史漏洞、CVE-2017-7921、CVE-2020-25078 等。
- **弱口令核查**：对授权目标，用小型内置默认口令字典做 HTTP Digest / RTSP 认证核查；强制限速、可一键关闭、命中即停止避免账户锁定。定位是"提醒用户仍在用默认口令"，非爆破攻击。

### 3.3 实时流媒体播放（stream）—— 最核心难点

系统 WebView **无法直接播放 RTSP**，需后端拉流并转换为浏览器可消费的格式。三种可选路线：

| 方案 | 后端处理 | 前端播放 | 延迟 | 复杂度 | 依赖 |
| --- | --- | --- | --- | --- | --- |
| A. HLS（推荐做 MVP） | ffmpeg 将 RTSP remux 成 HLS 切片，经内置 HTTP 服务提供 | `hls.js` | 高(3-6s) | 低 | 需 ffmpeg |
| B. fMP4 + MSE | Rust(`retina`) 拉 RTP/H.264 → 打包 fMP4 → 经本地 WS/HTTP 推给前端 `MediaSource` | MSE | 中(0.5-2s) | 中 | 纯 Rust 可行 |
| C. WebRTC | Rust(`retina`+`webrtc`/`str0m`) 建 PeerConnection 转发 RTP | 原生 `RTCPeerConnection` | 低(<0.5s) | 高 | 纯 Rust 可行 |

**推荐演进**：MVP 用方案 A（ffmpeg-sidecar，最快跑通多品牌兼容），第二阶段上方案 B（去掉转码、纯 remux、低延迟、无外部依赖），对多路低延迟预览再考虑方案 C。

**本地媒体服务**：后端用 `axum` 起一个仅监听 `127.0.0.1` 随机端口的 HTTP 服务，向前端提供 HLS/fMP4，避免把媒体流暴露到外部接口。

### 3.4 数据存储

- `sqlite`（`tauri-plugin-sql` 或 `rusqlite`）保存：目标/白名单、扫描任务、结果、审计日志。
- 快照图片与导出文件存到 app 数据目录（`tauri-plugin-fs` / `app_data_dir`）。

## 4. 技术选型

### 4.1 后端 Rust crates

| 用途 | crate |
| --- | --- |
| 异步运行时 | `tokio` |
| HTTP 客户端（Digest 认证/探测） | `reqwest` + `diqwest`（digest） |
| RTSP/RTP 拉流 | `retina` |
| ONVIF/SOAP | `onvif` 或手写 `quick-xml` |
| mDNS 发现 | `mdns-sd` |
| 本地媒体服务 | `axum` / `hyper` |
| WebRTC（阶段三） | `webrtc` 或 `str0m` |
| ffmpeg 调用（阶段一） | `ffmpeg-sidecar` 或 `tauri-plugin-shell` |
| 存储 | `rusqlite` / `sqlx(sqlite)` |
| 序列化 | `serde` / `serde_json` / `csv` |
| 并发限速 | `tokio::sync::Semaphore` / `governor` |
| 日志 | `tracing` |

### 4.2 前端

- React 19 + TypeScript（脚手架已就绪）、Vite 8。
- 播放：`hls.js`（HLS）、原生 `MediaSource`（fMP4）、原生 `RTCPeerConnection`（WebRTC）。
- 状态/数据：`zustand` 或 `@tanstack/react-query`；表格用 `@tanstack/react-table`；UI 库按喜好（Ant Design / shadcn）。
- Tauri 交互：`@tauri-apps/api` 的 `invoke` 调命令、`listen` 收事件（扫描进度、发现设备）。

### 4.3 需要引入的 Tauri 插件

`sql`、`fs`、`shell`（若用 ffmpeg sidecar）、`store`（配置）、`log`、`dialog`。

## 5. 前后端接口草案（Tauri command / event）

```ts
// commands (前端 invoke)
scan_start(opts: { cidr: string; ports: number[]; credCheck: boolean; rateLimit: number }): TaskId
scan_cancel(taskId: TaskId): void
device_list(taskId: TaskId): Device[]
audit_device(deviceId: string): AuditResult          // 指纹 + 漏洞比对
stream_open(deviceId: string, opts): { url: string }  // 返回本地 HLS/fMP4/WebRTC 地址
stream_close(sessionId: string): void
whitelist_add(target: string): void                   // 网段白名单，公网需二次确认
results_export(taskId: TaskId, fmt: "csv" | "json"): FilePath

// events (后端 emit → 前端 listen)
"scan://progress"   { taskId, scanned, total }
"scan://device"     Device                            // 发现一台即推一台
"scan://finished"   { taskId }
"stream://error"    { sessionId, message }
```

后端在 `scan_start` / `whitelist_add` 内部强制做 **RFC1918 校验 + 授权确认**，非白名单目标直接拒绝。

## 7. 可行性分析

### 7.1 技术可行性

- **脚手架已验证可用**：`pnpm build`（前端 tsc + vite）通过；`cargo check`（Tauri 2.9 后端）通过。基础工程链路成立。
- **发现/探测**：均为成熟的网络编程，Rust + tokio 完全胜任；ONVIF/RTSP 均有现成 crate（`onvif`、`retina`），风险低。
- **流媒体**：最大不确定性在 **多品牌 RTSP 兼容性** 与 **低延迟**。规避策略：MVP 用 ffmpeg 保证兼容，再逐步替换为纯 Rust remux。属"已知难点、有成熟解法"。
- **跨平台**：Tauri 2.0 支持 macOS/Windows/Linux；ffmpeg 走 sidecar 时需为各平台打包对应二进制，需在 CI 中处理。

### 7.2 主要风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 合规/滥用 | 高 | 私网默认限制、公网二次确认、审计日志、不含攻击载荷、启动授权确认 |
| RTSP 品牌兼容差异 | 中 | MVP 走 ffmpeg 转封装；建设备兼容性矩阵 |
| 弱口令核查触发账户锁定 | 中 | 限速、命中即停、可关闭、只用极小默认字典 |
| 大网段扫描耗时/被 IDS 拦截 | 中 | 并发信号量 + 令牌桶限速，建议先用 masscan 等缩小范围再导入 |
| 多路预览资源占用高 | 中 | 限制同时预览路数；预览按需拉流、关闭即释放 |
| ffmpeg 打包与许可 | 低 | 使用 LGPL 构建或让用户自带 ffmpeg 路径 |

### 7.3 结论

在"**限定于授权环境**"的前提下，本方案技术路径清晰、关键依赖成熟、脚手架已跑通，**具备可行性**。建议按下方里程碑分阶段推进，优先打通"发现 → 指纹 → 单路预览"的最小闭环。

## 8. 里程碑

1. **M1 骨架**（已完成）：Tauri 2.0 + React 脚手架，前后端可构建。
2. **M2 发现闭环**（已完成）：端口扫描 + ONVIF WS-Discovery + mDNS/DNS-SD 发现 + 结果表格 + 白名单/授权校验 + SQLite(rusqlite) 持久化与历史查询。
3. **M3 单路预览**（已完成）：ffmpeg 将 RTSP 转封装/转码为 HLS，经仅监听 `127.0.0.1` 的 `tiny_http` 媒体服务提供，前端 `hls.js` 低延迟播放。
4. **M4 指纹与漏洞比对**（已完成）：HTTP 指纹识别（Server/realm/正文厂商特征）+ 内嵌规则库比对（`src-tauri/rules/camera_cves.json`）+ Digest/Basic 弱口令核查（可关闭、限速、命中即停）+ 加固建议展示。
5. **M5 低延迟与多路**（已完成）：`retina` 纯 Rust RTSP→fMP4 remux + MSE 播放；ffmpeg fMP4 HLS（mse）与 MPEG-TS HLS 可选；多路网格预览（上限 4 路）+ `stream_list`。
6. **M6 打磨**（已完成）：首次启动授权确认、SQLite 审计日志、加固报告（Markdown/HTML）、GitHub Actions 跨平台打包 CI、README。

## 9. 本地开发 & 运行

```bash
pnpm install            # 安装前端依赖（已完成）
pnpm tauri dev          # 启动桌面开发（首次会编译 Rust，耗时较长）
pnpm build              # 仅构建前端产物
pnpm tauri build        # 打包桌面安装包
```

> 注：`pnpm tauri` 需要 `@tauri-apps/cli`（devDependencies 已含）。运行 `tauri dev` 前确保系统满足 [Tauri 2.0 前置依赖](https://v2.tauri.app/start/prerequisites/)（Rust、平台 WebView 等）。
